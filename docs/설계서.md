## 1. 문제 정의와 기획

**문제.** 다이어트 동아리에서 각자 오늘 뭘 했는지는 카톡에 흘러가고, 한 달 뒤에 남는 건 체중계 숫자 하나다.
그 숫자가 왜 그렇게 움직였는지 설명할 근거가 없다.

**해결.** 매일의 활동을 한 줄로 기록하고, 한 달치가 쌓이면 체중이 어느 방향으로 가고 있는지를
활동 기록과 나란히 보여준다. 체중이 주인공이고, 활동은 그 숫자의 근거다.

**주 사용자.** 다이어트 동아리 임원. 공용 기기에서 동아리 활동을 기록한다.

**과제 명세와의 관계.** 과제명은 "동아리 활동 기록 관리 웹앱"이다.
다이어트는 **차별화용 확장**이지 과제의 대체가 아니다. 필수 3기능이 화면 1급 시민이고,
체중·칼로리는 그 위에 얹은 것이다. 확장이 필수를 밀어내면 제출 요건에서 떨어진다.

| 명세 필수 | 우리 구현 |
|---|---|
| 활동 등록 | 활동명·날짜·장소·참여 인원·메모 + 확장 4필드 |
| 활동 목록 조회 | 최신순, 0건이면 안내 문구 |
| 활동 삭제 | 개별 삭제, `confirm()` 확인 |

| 명세 선택 | 우리 구현 |
|---|---|
| 월별 활동 횟수 통계 차트 | `Analytics.monthlyCount()` → CSS 가로 막대 |
| 참여 인원 합계 및 평균 | `Analytics.summary()` |
| JSON 내보내기 / 가져오기 | `Store.exportJson()` / `importJson()` |
| 반응형 레이아웃 | `style.css` |

체중 추이·칼로리 수지는 명세 목록 **밖의 자체 확장**이다. 위 항목을 대체하지 않는다.

## 2. 시스템 구조

### 모듈 분리의 이유

파일 하나로 만들면 210분 안에는 더 빨랐을 것이다. 셋으로 나눈 건 성능이나 재사용 때문이 아니라
**세 명이 동시에 다른 파일을 편집해야 병합 충돌이 안 나기 때문**이다.
역할 분담이 곧 파일 분할이고, 그래서 경계가 사람 단위로 그어져 있다.

```
        index.html
            │  script 3개를 순서대로 로드
            ▼
   ┌─────────────────────────────────────┐
   │  ui.js (동제)                        │  DOM · 이벤트 · 렌더링
   └───────┬──────────────────┬──────────┘
           │ Store.*          │ Analytics.*
           ▼                  ▼
   ┌───────────────┐   ┌──────────────────┐
   │ store.js (효민)│   │ analytics.js(준표) │
   │ 저장·검증·JSON │   │ 순수 집계 함수     │
   └───────┬───────┘   └──────────────────┘
           │ 유일한 접근점              ▲
           ▼                          │ 배열을 인자로 받을 뿐
   ┌───────────────┐                  │ Store를 모른다
   │  localStorage  │                  │
   │  key:activities│──────────────────┘
   └───────────────┘
```

**의존 방향은 한 방향이다.** `ui → store`, `ui → analytics`. 역방향과 `store ↔ analytics` 사이에는 화살표가 없다.

- `analytics.js`가 `Store`를 모르기 때문에 **준표는 효민을 기다리지 않고 지금 작업할 수 있다.** 배열을 손으로 만들어 테스트한다.
- `store.js`가 화면을 모르기 때문에 `alert` 대신 `errors` 객체를 돌려준다. 검증 결과를 어떻게 보여줄지는 동제가 정한다.
- `ui.js`가 `localStorage`를 직접 만지지 않기 때문에 저장 형식이 바뀌어도 `store.js`만 고치면 된다.

### 로드 순서

```html
<script src="js/store/store.js"></script>
<script src="js/analytics/analytics.js"></script>
<script src="js/ui/ui.js"></script>
```

`type="module"`을 쓰지 않는다. `file://`에서 ES 모듈은 CORS로 차단되어 화면이 백지가 된다.
심사자가 저장소를 받아 `index.html`을 더블클릭하는 것이 기본 실행 경로이므로, 이 제약이 스택 선택보다 우선한다.
각 파일은 전역 객체 `Store` / `Analytics` 하나씩만 노출한다.

### 데이터 흐름 — 단일 렌더 파이프라인

부분 갱신을 하지 않는다. **모든 변경 후 `render()` 전체를 다시 돌린다.**

```
[등록 / 삭제 / 가져오기 / 샘플생성]
            │
            ▼
      Store.<변경함수>          localStorage 갱신
            │
            ▼
        render()
            │
            ├─→ Store.getAll() ──┬─→ 목록 렌더링
            │                    │
            │                    └─→ Analytics.summary()
            │                        Analytics.monthlyCount()
            │                        Analytics.byCategory()
            │                        Analytics.weightTrend()  → 눈금 트랙
            │                        Analytics.kcalBalance()
            ▼
        화면 전체 일치
```

기록 수십 건 규모에서 전체 재렌더링의 비용은 체감되지 않는다.
반면 "삭제했는데 통계 숫자만 안 바뀐다" 같은 상태 불일치 버그는 **구조적으로 발생할 수 없게 된다.**
통계·목록·눈금이 전부 같은 `getAll()` 결과 하나에서 파생되므로 화면 안의 숫자가 서로 어긋나지 않는다.

## 3. 데이터 구조

localStorage 키 `"activities"`, JSON 배열. 활동 1건:

```js
{
  // 명세서 고정 7필드 — 이름 변경·삭제 금지
  id,           // string, Store가 발급
  title,        // "러닝 5km"
  date,         // "YYYY-MM-DD"
  place,        // "한강공원"
  memberCount,  // 1 이상 정수
  memo,
  createdAt,    // ISO 문자열, Store가 발급

  // 확장 4필드
  category,     // '유산소' | '근력' | '스트레칭'
  durationMin,  // 1 이상 정수
  weightKg,     // 선택 입력 — 미입력이면 null
  kcalIn        // 선택 입력 — 미입력이면 null
}
```

**고정 7필드는 덮지 않고 확장만 한다.** 개인 다이어트 기록으로 기울수록 `place`와 `memberCount`가
어색해지지만, 명세 필수 입력이므로 폼에서 빼지 않는다. 동아리 활동이라는 틀을 유지하는 필드다.

`kcalOut`은 **저장하지 않는다.** `durationMin`과 `category`로 `Analytics`가 매번 계산하는 파생값이다.
저장하면 원본이 수정될 때 어긋나고, 그 시점부터 화면의 두 숫자가 서로 다른 말을 하게 된다.
같은 이유로 통계 결과·주간 요약도 저장하지 않는다.

## 4. 미결정 사항 확정

`CLAUDE.md`에 "정하고 적어둔다"로 남아 있던 항목들이다. **정해지지 않은 채 각자 구현하면 통합 시점에 어긋난다.**
아래로 확정한다.

### ① 미입력은 `null`로 통일한다

`js/store/CLAUDE.md`가 "필드를 아예 넣지 않거나 `null` — 둘 중 하나로 통일"로 열어둔 것을 **`null`로 닫는다.**

`JSON.stringify({ weightKg: undefined })`는 `"{}"`다. **키가 사라진다.**
내보내기 → 가져오기를 하면 필드 유무가 달라져서, `importJson`이 `add`와 같은 검증을 태울 때 분기가 갈린다.
`null`은 JSON에 그대로 살아남으므로 왕복해도 형태가 같다.

읽는 쪽은 가드 하나로 통일한다. 준표·효민이 같은 판정을 쓴다.

```js
const has = v => v != null && !Number.isNaN(v);
```

`v != null`은 `null`과 `undefined`를 동시에 잡는다. 느슨한 비교를 쓰는 유일하게 정당한 자리다.
가져온 파일에 `undefined` 대신 키가 없는 기록이 섞여 들어와도 이 가드가 함께 막는다.

### ② `weightTrend`는 그날 **마지막** 기록을 쓴다

`js/analytics/CLAUDE.md`가 "마지막 하나 또는 평균 — 정하고 적어둔다"로 열어둔 것을 **마지막**으로 닫는다.

체중은 통계량이 아니라 **측정값**이다. 아침 69.8 / 저녁 68.4를 평균 내면 69.1이 나오는데,
이건 그날 체중계에 한 번도 찍힌 적 없는 숫자다. 없는 측정을 화면에 그리지 않는다.

같은 날짜가 여러 건이면 `createdAt`이 가장 큰 것을 쓴다.

```js
const m = new Map();
[...list]
  .sort((a, b) => (a.createdAt < b.createdAt ? -1 : 1))
  .forEach(r => { if (has(r.weightKg)) m.set(r.date, r.weightKg); });
// 뒤에 오는 것이 앞을 덮는다 → 그날 마지막 측정만 남는다
```

### ③ `kcalBalance`의 포함 조건

루트 `CLAUDE.md`는 "둘 중 하나라도 있는 날만"이라 적혀 있으나, `kcalOut`은 `durationMin`과 `category`만
있으면 **항상 계산된다.** 그래서 이 조건은 실질적으로 거의 모든 기록일을 통과시킨다. 조건 자체는 그대로 두되,
화면에서 오해가 없도록 이렇게 확정한다.

- 같은 날짜는 **합산**한다. 하루에 두 번 운동하면 소모도 두 번이다
- `kcalIn`이 없는 날은 `kcalIn: null`, `net: null` — **0으로 채우지 않는다**
- 화면에는 `0`이나 `NaN`이 아니라 `—`로 표시한다
- `category`가 `KCAL_PER_MIN` 표에 없으면 그 기록은 `kcalOut` 계산에서 제외한다

`KCAL_PER_MIN = { 유산소: 10, 근력: 6, 스트레칭: 3 }`은 **근사치다.**
체중을 반영한 MET 공식으로 정교하게 만들지 않는다 — 시간이 없고, 데모에서 그 차이가 보이지 않는다.
대신 화면에 "운동 시간과 종목으로 추정한 값" 한 줄을 적어 근거 없는 정밀도를 주장하지 않는다.

### ④ `importJson`은 `createdAt`을 보존하고 `id`는 재발급한다

`add`는 `createdAt`을 새로 만들지만, **`importJson`은 만들지 않는다.**
새로 만들면 가져온 기록 전부가 "지금"이 되어 원래의 시간 순서를 잃는다.
내보내기 → 가져오기가 무손실이어야 백업 기능으로서 의미가 있다.

- `createdAt`이 유효한 문자열이면 **보존**, 없거나 깨졌으면 새로 발급
- `id`는 **항상 재발급** — 기존 기록과 충돌하면 삭제가 엉뚱한 걸 지운다
- 검증을 통과하지 못한 항목은 `skipped`로 세고 나머지는 넣는다. 파일 하나가 통째로 거부되지 않는다
- 파싱 실패·배열 아님은 예외를 던지지 않고 `{ ok: false, message }`로 돌려준다

### ⑤ 목록 정렬 기준을 `date` 우선으로 바꾼다 ⚠️ 계약 변경

**현재 계약은 `Store.getAll()`이 `createdAt` 내림차순이다. 이대로 두면 샘플 데이터에서 눈에 보이는 버그가 난다.**

`seedSampleData()`는 최근 30일치를 **반복문 한 번에** 만든다. 그러면 `createdAt`이 전부 지금 시각이고
밀리초 단위로만 다르다. `createdAt`으로 정렬하면 목록이 **생성 루프 순서**대로 나오고, 날짜순이 아니다.
심사자가 샘플 데이터를 켜고 목록을 보는 순간 "최신순 아닌데?"가 된다. 명세 필수 요건이라 직접 감점이다.

두 가지를 함께 적용한다.

```js
// store.js — getAll()
[...list].sort((a, b) =>
  a.date !== b.date
    ? (a.date < b.date ? 1 : -1)          // date 내림차순 (활동일 기준)
    : (a.createdAt < b.createdAt ? 1 : -1) // 같은 날이면 입력 늦은 것이 위
);
```

그리고 `seedSampleData()`는 **`createdAt`을 해당 `date`에 맞춰 생성한다.** 30일 전 기록의 `createdAt`이
오늘이면 정렬을 고쳐도 데이터 자체가 거짓말을 한다.

"최신순"을 심사자는 **활동 날짜 기준**으로 읽는다. 과거 활동을 나중에 입력했다고 목록 맨 위에 뜨는 것도
사용자 입장에서는 틀린 동작이다. 두 근거가 같은 방향을 가리킨다.

> **이건 세 명 합의가 필요한 계약 변경이다.** 반영하면 루트 `CLAUDE.md`의 인터페이스 계약과
> `js/store/CLAUDE.md`의 `getAll` 주석을 함께 고친 커밋을 남긴다.

**설계 판단**

- 체중 숫자를 크게 가되 **화면을 독점시키지 않는다.** 히어로가 첫 화면을 다 먹는 랜딩페이지 구성을
  따라가면 필수 3기능이 스크롤 아래로 밀린다. 우리는 랜딩페이지가 아니라 도구다.
- 목록의 각 행에 **활동명·날짜·장소·참여 인원이 전부 보인다.** 체중만 보이는 행은 명세 위반이다.
- 위계는 **선 두께**로 만든다(8px / 3px / 1px). 영양성분표의 방식이다. 색과 크기로 대신하지 않는다.
- `--needle` 빨강은 **"오늘" 한 곳에만** 쓴다. 두 군데 이상 쓰고 싶어지면 설계가 흐트러진 것이다.
  증감은 색이 아니라 바늘 위치와 ▲▼로 나타낸다.
- 애니메이션은 **바늘 이동 `.2s` 하나뿐이다.** 움직임이 많을수록 AI가 찍어낸 화면처럼 보인다.

**차트 라이브러리를 쓰지 않는다.** CDN은 명세상 허용되지만 행사장 네트워크가 끊기면 화면이 통째로 죽는다.
Chart.js 축·옵션을 맞추는 데 30분이 날아가는데, CSS 막대(`width: {비율}%`)는 10분이고 디자인 방향에도 맞는다.
70분밖에 없는 지금은 선택의 여지가 없다.

**엣지 케이스**

| 상황 | 화면 |
|---|---|
| 기록 0건 | 목록에 안내 문구. 눈금 트랙과 통계 섹션은 **숨긴다** (빈 눈금은 고장으로 보인다) |
| `weightKg` 있는 기록이 1건 | 최고=최저라 0으로 나눈다. 바늘을 **50%** 에 고정 |
| `kcalIn` 없는 날 | `—` (`0`도 `NaN`도 아니다) |
| 폰트 CDN 실패 | `font-family`에 폴백을 적어 레이아웃이 그대로 서게 한다 |

## 6. 잘라낸 것과 그 이유

기획 단계에서 검토했다가 뺀 것들이다. 보고서 5장 "한계와 개선 방향"의 근거다.

| 뺀 것 | 이유 |
|---|---|
| **3D 인체 마네킹** (Three.js) | GLTF 모델 로딩이 `file://`에서 CORS로 차단된다. localhost 서버가 필수가 되는데 실행 방법이 "더블클릭"이어야 한다. 모델 파일 확보도 미해결. 낙관적으로 90분 |
| **스크롤 프레임 애니메이션** | 기술은 30줄이면 되지만 프레임 이미지 24~60장을 만들 방법이 없다. 결국 3D 렌더링이 필요해 위와 같은 문제로 돌아온다 |
| **SVG 인체 + 부위 하이라이트** | 자산 없이 가능한 대안이었으나, 부위를 저장하려면 `bodyParts` 필드가 필요하고 이는 종목(`category`) 하나로 대체 가능하다. 눈금 트랙이 시그니처 역할을 이미 한다 |
| **동아리원별 현황판** (`memberId`) | localStorage는 브라우저 하나에 갇혀 있어 진짜 공유가 안 된다. 서버는 명세 금지. JSON 수동 교환으로 대체했다. 단일 사용자 모델로 축소 |
| **머신러닝 기반 다음 달 계획 제안** | 오늘 만든 앱에 학습 데이터가 없다. 모델 파일 로딩도 `file://`에서 막힌다. 통계 집계로 대체 |
| **MET 공식 칼로리** | 체중별 정밀 계산은 데모에서 차이가 보이지 않는다. 종목별 분당 근사치로 충분하고, 추정치임을 화면에 밝힌다 |
| **활동 수정 기능** | 명세 선택 항목이지만 필수가 아니다. 70분에서는 삭제 후 재등록으로 갈음한다 |
| **활동명·장소 키워드 검색** | 선택 항목 중 가장 저렴하나, 필수 3기능과 통계가 끝난 뒤에만 손댄다 |

**사용자 식별자는 한 곳에 모아둔다.** 지금은 단일 사용자지만 변수 하나에만 두면
나중에 그 자리에 인증을 끼울 수 있다. 인증·회원가입·권한 관리는 만들지 않는다.

## 부록: 통합 확인 목록

`main`에서 `index.html`을 크롬으로 열고 손으로 확인한다.

- [ ] 활동명 비우고 저장 → 막히고 **활동명 옆에** 메시지
- [ ] 날짜를 내일로 → 막힘
- [ ] 참여 인원 `0` / `-1` / `2.5` → 각각 막힘
- [ ] 종목에 없는 값 → 막힘
- [ ] 체중란을 비우고 저장 → 저장되고, 저장된 값이 `0`이 **아님**
- [ ] 저장 → 목록 맨 위
- [ ] 삭제 → 확인창, 취소하면 안 지워짐
- [ ] 전부 삭제 → 빈 목록 안내 문구
- [ ] 0건 상태에서 통계 → `NaN` / `Infinity` / 빈 막대 없음
- [ ] 샘플 데이터 생성 → **목록이 날짜 내림차순**(§4-⑤)
- [ ] 내보내기 → 가져오기 → 건수와 순서가 그대로
- [ ] 모바일 폭(375px)에서 가로 스크롤 없음
- [ ] 콘솔 에러 없음
