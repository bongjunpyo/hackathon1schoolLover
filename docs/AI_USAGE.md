# Claude Code 활용 기록

에이전트에 위임한 작업을 **위임 방식과 검증 방법을 쌍으로** 남긴다.
실패 사례도 적는다 — 검증 루프가 실제로 돌았다는 증거다.
프롬프트는 요약하지 않고 **실제 입력한 문장 그대로** 옮긴다.

결과 보고서 3장이 이 문서에서 나온다.

---

## 데이터 계층 — 효민

### 1. 기획 단계: 요청이 명세와 충돌한 것을 잡아낸 사례

**실제 입력한 문장**

> 운동동아리를 만들려고해. 헬스 운동을 기록하고 동아리원의 오늘 운동 부위 등을 볼 수 있는. 알람도 가게끔. 앱이 나을까 웹이 나을까?

**받은 결과**

앱/웹 답변보다 먼저 **두 기능이 명세 제약에 걸린다**는 지적이 돌아왔다.

- "동아리원의 오늘 운동 부위 보기" — localStorage는 브라우저 하나에 갇혀 있어 기기 간 공유가 불가능하다. 서버가 필요한데 명세가 금지한다
- "알람" — 브라우저 알림은 페이지가 열려 있는 동안만 뜬다. 게다가 `file://`로 열면 알림 권한 요청 자체가 차단된다

**만족스러웠는가**

만족스러웠다. 요청대로 만들었다면 시연 중에 동작하지 않는 기능 두 개를 껴안고 갔을 것이다.

### 2. 프롬프트 개선 사례 (필수 항목)

**처음 요청한 내용**

> json 파일로 저장해서 하면 안되나?

공유 문제를 저장 형식으로 풀려고 했다.

**결과가 기대와 달랐던 지점**

- 브라우저 JS에는 디스크 쓰기 권한이 없다. 할 수 있는 건 다운로드 폴더에 파일을 떨구는 것뿐이다
- 읽기도 `file://`에서는 `fetch('./data.json')`이 CORS로 막힌다
- **더 근본적으로는, JSON 파일도 내 컴퓨터 안에 있다.** 공유 문제는 저장 형식이 아니라 네트워크 너머의 공용 저장소가 있어야 풀린다

**요청을 어떻게 고쳤는지**

"공유를 어떻게 구현할까"에서 **"서버 없이 공유 비슷한 것을 어떻게 만들까"** 로 질문을 바꿨다.
그 결과 명세서 선택 기능 목록에 있는 **JSON 내보내기/가져오기**가 답이 됐다.
localStorage를 정본으로 두고 JSON은 주고받는 봉투 역할만 한다.

**고친 뒤 무엇이 달라졌는지**

- 구현 불가능한 기능을 붙잡고 있다가 명세서가 인정하는 선택 기능 하나를 얻었다
- 이 판단이 그대로 보고서 5장 "한계와 개선 방향"이 됐다 — *현재는 수동 JSON 교환, 서버가 있었다면 실시간 동기화*

### 3. 컨셉이 명세 검증 요건과 충돌한 것을 잡은 사례

**상황**

"이번 주 다이어트 **계획**을 입력한다"가 원래 컨셉이었다.
그런데 명세서 입력값 검증 요건에 **"날짜는 미래 날짜 입력 불가"** 가 있다. 계획은 본질적으로 미래 날짜다.

**해결**

컨셉을 반 바퀴 돌렸다. 사용자가 계획을 입력하는 게 아니라,
**오늘 한 것을 기록** → 앱이 패턴을 분석 → **다음 계획을 제안**하는 흐름으로 바꿨다.

미래 날짜 입력이 사라져 검증 요건을 100% 지키면서, 분석 파트가 앱의 핵심이 됐다.

### 4. 오류 해결 사례 (필수 항목) — 랭킹이 정반대로 나온 문제

**발생한 오류**

`seedSampleData()`를 만들고 `analytics.js`를 붙여 통합 테스트를 돌렸더니 감량 효과 랭킹이 뒤집혀 나왔다.

```
topFoods   : 피자, 삼겹살, 고구마        <- 감량 1위가 피자?
worstFoods : 단백질쉐이크, 라면, 치킨    <- 회피 대상이 단백질쉐이크?
```

샘플 데이터에는 분명히 닭가슴살·샐러드에 감량 효과를, 치킨·피자에 증량 효과를 심어뒀다.

**원인 파악 과정**

증상이 "틀린 값"이 아니라 **"정확히 반대"** 였다. 무작위 오류가 아니라 부호나 방향이 어긋났다는 뜻이라
귀속 로직부터 읽었다. `analytics.js`의 `dailyWeightChange`에서 찾았다.

```js
changes[from] = (weightByDate.get(to) - weightByDate.get(from)) / gapDays;
```

기록 **이후**의 체중 변화를 그 기록에 귀속시킨다. "오늘 먹은 것이 다음 측정에 나타난다"는 모델이고,
이건 맞다. 문제는 내 `seedSampleData()`가 오늘의 선택을 **오늘 체중에 이미 반영**해서 저장했다는 것이다.
한 칸씩 밀린 채로 귀속되니, 플랜이 순환하면서 다음 날 플랜의 효과가 오늘 항목에 붙었다.

**해결 방법**

기록 시점의 체중을 **선택 반영 전 값**으로 바꿨다.

```js
// 이 기록의 체중은 오늘 선택을 반영하기 전 값이다.
const weightToday = weight;
weight += sampleWeightDelta(plan);   // 오늘의 선택은 다음 기록에 나타난다
```

```
topFoods    : 계란, 현미밥, 닭가슴살
worstFoods  : 치킨, 탄산음료, 피자
topExercises: 자전거, 등산, 수영
```

**이 과정에서 배운 점**

- **모듈이 각자 맞아도 모델이 어긋나면 통합에서 터진다.** 두 파일 다 자기 기준으로는 정상이었다.
  단위 테스트만 돌렸다면 끝까지 못 잡았을 것이고, 심사 중에 "피자가 감량 1위"인 화면을 보여줬을 것이다
- **증상의 모양이 원인을 가리킨다.** 값이 틀린 게 아니라 반대로 나온다는 건 방향 문제라는 신호였다
- 남의 코드를 의심하기 전에 계약 문서가 아니라 **실제 구현을 읽어야 한다.**
  결과적으로 준표의 코드는 문제가 없었고 내 샘플이 틀렸다

### 5. 위임과 검증을 쌍으로 — `store.js`

**실제 입력한 문장**

> 오케이 명세서는 더 이상 작성 안 해도 돼? 그럼 바로 store.js 들어가자.

**위임 방식**

`js/store/CLAUDE.md`의 작업 순서를 그대로 따라 **기능 하나 = 커밋 하나**로 쪼갰다.
한 번에 전체를 만들게 하지 않았다. 매 커밋마다 검증을 먼저 돌리고 결과를 커밋 본문에 남겼다.

**검증 방법**

브라우저 없이 확인하려고 node에 `localStorage`를 흉내 낸 객체를 주입해 `store.js`를 그대로 실행했다.
저장소 파일은 손대지 않았고 테스트 스크립트는 저장소에 넣지 않았다.

| 커밋 | 범위 | 검증 |
|---|---|---|
| `56e0c31` | `getAll` / `add` + 명세 필수 검증 3종 | 19건 |
| `0ad4eee` | 확장 필드 6종 검증·정규화 | 21건 |
| `c1e1d87` | `remove` / `clearAll` | 8건 |
| `80de298` | `seedSampleData` | 20건 |
| `3b9e2b6` | `exportJson` / `importJson` | 18건 |

**총 86건.** 확인한 것 중 실제로 버그를 막은 항목:

- 참여 인원 `0` / `-1` / `2.5` / `''` / `'abc'` 를 전부 거부하는지
  (`parseInt('2.5')`는 `2`가 되어 통과처럼 보인다. `Number.isInteger`를 써야 한다)
- 체중란을 비웠을 때 `0`이 아니라 `null`로 저장되는지
  (`Number('')`는 `0`이다. 그냥 넘기면 체중 0kg가 평균에 섞인다)
- JSON 내보내기 → 가져오기 왕복에서 `null` 필드의 키가 살아남는지
  (`undefined`였다면 `JSON.stringify`에서 키째 사라진다)
- 통계 함수에 `NaN` / `Infinity`가 새지 않는지

### 6. 문서에서 잡은 것 — 열려 있던 결정 5건

`CLAUDE.md`를 읽고 설계서를 쓰는 과정에서 **"정하고 적어둔다"로 열린 채 방치된 항목**들을 찾았다.
각자 구현했다면 통합 시점에 어긋났을 것들이다.

| 항목 | 확정 | 근거 |
|---|---|---|
| 미입력 표현 | `null` | `undefined`는 JSON 왕복에서 키가 사라진다 |
| `weightTrend` 같은 날 중복 | 마지막 측정값 | 평균은 체중계에 찍힌 적 없는 숫자를 만든다 |
| `kcalBalance` 포함 조건 | 날짜별 합산, 없으면 `null` | `kcalOut`은 항상 계산돼 조건이 사실상 무의미했다 |
| `importJson`의 `createdAt` | 보존, `id`는 재발급 | 새로 만들면 가져온 기록이 전부 "지금"이 된다 |
| **목록 정렬 기준** | `date` 우선 | 아래 참조 |

정렬 기준은 실제 버그였다. `getAll()`이 `createdAt` 내림차순이면,
`seedSampleData()`가 반복문 한 번에 만든 30일치는 `createdAt`이 전부 같은 시각이라
목록이 **날짜순이 아니라 생성 순서**로 나온다. 명세서 필수 요건인 "최신순"이 깨지는 자리였다.

## 데이터 처리 — 준표

### 1. 제약 충돌을 먼저 잡아낸 사례

**실제 입력한 문장**

> ml작업할 건데 어떤 식으로 할 거냐면 한 달동안 이 사람이 어떤 운동을 하였고, 어떤 식단을 하였으며,
> 얼마나 몸의 변화가 일어났는지 분석하고 그 다음에는 오늘은 어떤 걸 추천하는 지 날씨와 오늘의 식단을
> 통해서 추천하는 거 어때 ? 동아리는 주제는 다이어트 동아리야. 우리는 웹으로 구현할거야.

**받은 결과**

ML 방식을 답하기 전에 제약 충돌 3건을 먼저 지적받았다.

1. **"백엔드" 역할이 성립하지 않는다** — 명세가 서버·DB를 금지한다. 데이터 계층(저장)과 데이터 처리(계산)로 나누는 게 맞다
2. **오늘 만든 앱의 localStorage는 0건이다** — 한 달치 분석을 시연하려면 샘플 생성이 명시적 기능으로 있어야 한다
3. **스키마가 템플릿에 고정되어 있다** — 지우지 말고 확장해야 한다

그 다음 ML 방식으로 TensorFlow.js 대신 **순수 JS 최소자승 회귀 + 피어슨 상관**을 권고받았다.
외부 의존이 0이라 데모 중에 터지지 않고, 보고서에 수식을 적을 수 있다는 이유였다.

**만족스러웠는가**

만족스러웠다. TensorFlow.js를 골랐다면 남은 130분을 브라우저 학습 디버깅에 썼을 것이다.
특히 `analytics.js`가 `Store`를 모르게 설계하자는 제안이 결정적이었다 —
**`store.js`가 없던 시점에 배열을 손으로 만들어 통계 함수를 전부 완성하고 검증**할 수 있었다.

### 2. 프롬프트 개선 사례 (필수 항목)

**처음 요청한 내용**

> 날씨에 따라 그럼 사람들이 어떤 스포츠를 선호하는지도 찾아서 자세히 어떤 운동을 어떤 시간대에 하면
> 좋은지도 같이 분석해서 덧붙이면 좋을 것 같아.

**결과가 기대와 달랐던 지점**

요청대로 **날씨를 중심에 둔 기능**이 나왔다. Open-Meteo 예보를 받아 체감온도·강수확률로 시간대를
점수화하고 최적 2시간 구간을 고르는 엔진이었다. 동작은 했지만 방향이 어긋나 있었다.

- 주인공이 **날씨**가 되어 있었다. 정작 알고 싶은 건 "내 몸에 뭐가 효과 있었나"였다
- 운동 분류가 카테고리 3종 단위라 거칠었다. "러닝이 효과적"이 아니라 "유산소가 효과적"까지밖에 안 나온다
- **식단 분석이 아예 없었다.** `kcalIn`(칼로리 총량)만 있고 음식 종류가 없었다
- 추천이 오늘 하루치뿐이라 "다음 날짜들"이라는 요구를 만족하지 못했다

**요청을 어떻게 고쳤는지**

> 지금 날씨로 예측 ml이 주요 기능이 아니야. 내 몸이 어떤 음식과 어떤 운동에서 가장 체중 감량이 많이
> 되었고, 그 중에서도 top3를 매겨 다음 날짜들에 맞춰서 날씨 기준으로 잡고 예측을 해주는 거야.

**무엇이 본체이고 무엇이 보조인지 명시**했다. 처음 요청은 "날씨에 따라 ~도 덧붙이면"이라는
추가 요청 형태여서, 무엇을 중심에 둘지가 빠져 있었다.

**고친 뒤 무엇이 달라졌는지**

| | 처음 | 고친 뒤 |
|---|---|---|
| 본체 | 날씨 기반 시간대 추천 | **개인 효과 랭킹** (날씨는 배치 필터로 강등) |
| 분석 단위 | 카테고리 3종 | 개별 운동 5종 + 개별 음식 12종 |
| 식단 | 없음 | `foods` 필드 추가, 음식별 감량 기여도 산출 |
| 계산 모델 | 주간 상관분석 | 귀속(attribution) |

```
Δw(d) = (다음 기록일 체중 − 당일 체중) / 경과일수     하루당으로 정규화
        경과일수 3일 초과 구간은 인과를 특정할 수 없어 버린다
그날 한 운동과 먹은 음식 각각에 Δw(d) 를 귀속 -> 항목별 평균으로 정렬
표본 3건 미만은 순위에서 제외, 양수 항목은 '회피 항목'으로 분리
```

**얻은 교훈.** "무엇을 추가할지"보다 **"무엇이 중심인지"를 먼저 말해야 한다.**
추가 요청 형태로 말하면 AI는 직전 맥락을 중심으로 삼는다.

### 3. 위임과 검증을 쌍으로 — `analytics.js`

`Store`가 없어도 되는 설계라 **배열을 손으로 만들어** 검증했다. 위임한 것마다 확인한 내용이다.

| 위임한 것 | 검증 방법과 결과 |
|---|---|

### 4. 스스로 만든 결과물에서 결함을 찾은 사례

날씨 추천 엔진을 만들고 출력을 읽었더니 결함 4건이 보였다. 코드가 도는 것과 결과가 말이 되는 것은 다르다.

```
매일 러닝만 추천        Top3를 뽑아놓고 1위만 반복 배치. 로테이션이 없다
"더움 날씨다 (체감 23.8도)"  버킷은 일평균 기온, 표시는 추천 시간대 체감. 앞뒤가 안 맞는다
비 오는 날 한강공원 야외    안전 가드가 폭염·한파만 잡고 비는 안 잡는다
요가(+0.05kg)가 감량 Top3에  증량 항목이 감량 순위에 들어간다
```

넷 다 고쳤다. 특히 마지막은 사용자가 요구한 "**가장 감량이 많이 된** top3"와 정면으로 어긋나서,
`onlyLosing` / `onlyGaining`으로 나누고 증량 항목은 **회피 항목**으로 분리했다.

`comfortScore`도 고쳤다. 뺄셈식이 극단 기온에서 0으로 포화돼 **34도와 38도를 동점 처리**했다.
포화되지 않는 곡선으로 바꿔 더운 쪽이 항상 낮은 점수를 받게 했다.

### 5. `recommend.js`를 B-2로 연기한 판단 (이슈 #2)

날씨 기반 7일 계획을 완성했는데, 효민이 이슈 #2에서 **순서 문제**를 제기했다.

1. `recommend.js`에 **전역 노출이 없어 로드해도 `loadPlan`을 호출할 방법이 없다**
2. 런타임에 외부 API를 치는데, 심사자의 실행 경로가 `file://`이라 Origin이 `null`이고 fetch가 막힐 수 있다
3. 계약 5종은 전부 동기 순수 함수인데 `loadPlan`만 `async`라 UI 통합 방식이 다르다

**셋 다 사실이라 수용했다.** 기능을 버리지 않으면서 데모 리스크를 없애는 방향으로 고쳤다.

- `Recommend` 전역 객체로 노출
- `loadPlan`이 `throw` 하지 않고 `{ ok: false, reason }`을 돌려준다 — 네트워크가 죽어도 추천 영역만 접히고 나머지 화면은 산다
- `buildPlan(activities, forecast, past)`는 예보를 인자로 받는 순수 함수라 네트워크 없이 시연할 수 있다
- 예보 배열에 `null`이 섞여 와도 죽지 않도록 시간별/일별 양쪽에 가드

검증: 전역 노출 확인, 가짜 예보 주입으로 네트워크 없이 계획 2일 생성, `fetch` 강제 실패 시 `ok:false` 반환,
실제 API 정상 호출 3일 생성, 기록 0건일 때 사유 문자열 반환.

**배운 점.** 내 코드에 대한 지적을 방어하는 것보다 **지적이 사실인지 먼저 확인**하는 게 빨랐다.
셋 다 실제로 재현됐고, 고치고 나니 기능을 지키면서 위험만 걷어낼 수 있었다.

### 6. 오류 해결 사례 — 화면이 통째로 비었다

마감 14분 전, 세 브랜치를 합치고 화면을 처음 열었더니 **필수 3기능이 하나도 렌더되지 않았다.**
콘솔 에러는 `favicon.ico` 404 하나뿐 — **에러 없이 조용히 실패하는 상태**였다.

로드 순서와 `type="module"` 미사용을 확인(정상)한 뒤 콘솔에서 모듈 정의를 봤다.

```
typeof Store  -> "object"   정의되어 있다      window.Store     -> undefined   <-- 여기
typeof Analytics -> "object"                   window.Analytics -> undefined
```

`ui.js`의 `ready()`가 `window[name]`을 보는데, `store.js`와 `analytics.js`는 둘 다 최상위 `const`로 선언한다.
**최상위 `const`·`let`은 전역 렉시컬 스코프에 들어갈 뿐 `window`의 프로퍼티가 되지 않는다.**
`var`나 함수 선언이었다면 붙었을 것이다.

각 모듈 끝에 `window.Store = Store;` / `window.Analytics = Analytics;` 한 줄씩 추가해 해결했다.
`CLAUDE.md`가 "전역 객체로 노출한다"고 한 계약을 실제로 만족시키는 방향이라 `ui.js`를 고치는 쪽보다 변경이 작았다.

**배운 점**

- **"에러가 없다"가 "정상이다"는 아니다.** 존재 확인이 조용히 실패하면 아무 흔적도 남기지 않는다
- **세 파일 모두 자기 기준으로는 계약을 지켰다.** *전역*이라는 단어의 해석이 달랐을 뿐이다.
  계약은 문장이 아니라 **실행되는 코드로 확인해야 한다**
- **통합 확인을 마지막에 몰면 남는 시간이 없다.** 모듈 단위 테스트는 셋 다 통과하고 있었다

### 7. 마감 후 보완 — 만든 것이 화면에 닿지 않고 있었다

총평 뒤에 확인해보니 `Analytics.topFoods()`가 정상 값을 돌려주는데 **`ui.js`가 호출하지 않아
감량 효과 Top3가 화면에 없었다.** 차별화 기능이 사용자에게 닿지 않은 상태로 제출된 것이다.

렌더 블록을 추가했다(PR #11). `js/ui/CLAUDE.md`의 디자인 규칙을 따라
증감을 색으로 칠하지 않고 **방향 삼각형(▼ 감량 / ▲ 증량)** 으로 표시했고,
기존 `.table` 스타일을 재사용해 `style.css` 변경이 0줄이다.

**배운 점.** 엔진이 검증을 통과했다고 기능이 완성된 게 아니다.
**사용자 화면까지 닿았는지 확인하는 것이 마지막 검증**인데, 계층을 나눠 작업하면 이 확인이 아무의 담당도 아니게 된다.

## 팀 차원의 판단 — 이슈 #2

**상황.** 준표가 `BJP` 브랜치에 감량 효과 랭킹과 날씨 기반 계획 추천을 구현했는데,
방향 전환 시점에 공유되지 않아 인터페이스 계약에 없었다. 15:20까지 결정이 필요했다.

**검토 과정.** 이슈에 적힌 것 외에 `BJP` 브랜치 코드를 직접 읽고 두 가지를 추가로 확인했다.

1. **랭킹 함수 4종은 이미 `Analytics` 전역에 노출되어 있었다.** `recommend.js` 없이도 랭킹은 동작한다.
   즉 랭킹만 살리는 데 드는 추가 작업이 이슈에 적힌 것보다 훨씬 적었다
2. **`recommend.js`는 런타임에 외부 API를 친다.** 심사자의 기본 실행 경로가
   `index.html` 더블클릭(`file://`)인데 Origin이 `null`이라 fetch가 막힐 수 있고,
   행사장 네트워크가 끊기면 기능이 통째로 죽는다

**결정.** B(살린다)를 택하되 두 단계로 쪼갰다.

- **B-1 감량 효과 랭킹** — 네트워크 불필요. 스키마 2필드만 추가하면 된다. 지금 한다
- **B-2 날씨 기반 계획** — 네트워크 필요. 필수 기능과 B-1이 끝난 뒤에만 검토한다

**결과.** 준표가 지적을 수용해 `recommend.js`에 전역 노출과 실패 흡수(`{ ok: false, reason }`),
오프라인용 순수 함수 경로를 추가했다. 기능을 버리지 않으면서 데모 리스크를 제거했다.

**부수 효과.** 랭킹을 살리기로 하면서 `seedSampleData()` 규칙이 랭킹과 충돌하는 것을 발견했다.
원래 "일부 기록의 `weightKg`를 비운다"였는데, 랭킹은 체중이 매일 있어야 동작한다.
`weightKg`는 전 기록에 넣고 미입력 검증은 `kcalIn` 쪽으로 옮겼다.

## 회고

**잘 된 것**

- `CLAUDE.md`를 구현 전에 쓰고 담당별로 나눈 것. 파일 경계가 사람 경계와 같아서 병합 충돌이 없었다

- `CLAUDE.md`에 "정하고 적어둔다"로 열어둔 항목들이 실제로 닫히지 않은 채 구현이 시작됐다.
